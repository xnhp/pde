# Pinned runtime bundles (why `materializeRuntime` doesn't call p2.director anymore)

`tools/api-analyzer`, `tools/target-installer`, `tools/workspace-setup`, and `tools/jdt-build`
each need a real Eclipse/Equinox runtime (a `plugins/` directory of OSGi bundle jars) to run a
headless application. Historically that runtime was assembled fresh on every build by running
`p2.director` against a locally-published SDK repo (plus a remote fallback, see
`p2Repositories` in `gradle.properties`).

## The problem

Each tool's OSGi "app bundle" jar embeds the whole `pde-resolver` module as a `Bundle-ClassPath`
lib entry, so **any change to `pde-resolver`** invalidates the app bundle jar for all four tools
simultaneously, which invalidates their `p2.director` resolution cache too. `p2.director`
dependency resolution is expensive (measured 20-30s per tool, serial) and running it concurrently
for multiple tools makes things *worse*, not better -- these are unconstrained-heap JVMs doing
real OSGi dependency-graph solving, and they contend hard for CPU/RAM (measured: one invocation
alone going from 24s solo to 2m30s under 3-way concurrency). So a `pde-resolver` change used to
cost 60-90s+ of serial `p2.director` time on every `installDist`, which made iteration painfully
slow.

## The fix: pin the resolved bundle set

`p2.director`'s only real job here is: *resolve a fixed set of top-level IUs into their full
transitive closure, and copy those jars into a directory.* Nothing about p2's own provisioning
model (profiles, `.p2` metadata) survives past that copy -- the CLI itself regenerates
`bundles.info`/`config.ini` from scratch every time it unpacks a runtime archive, by reading the
`Bundle-SymbolicName`/`Bundle-Version` straight out of each jar's `MANIFEST.MF`
(`ensureEquinoxAppRuntimeConfiguration` in
`core/pde-launch-engine/src/main/kotlin/cn/varsa/pde/resolver/cli/Main.kt`). Filenames and p2's
own installed-bundle metadata are never read back.

That means we don't need p2's resolver on every build -- we need its **result**, which barely
ever changes (only when the local Eclipse SDK version changes, or a tool's `installIUs` list
changes). So each tool now has two task chains:

- **`materializeRuntime`** (the name varies per tool: `materializeRuntime`,
  `materializeWorkspaceSetupRuntime`, `materializeJdtBuildRuntime`) -- the FAST default path, part
  of `assemble`/`installDist`. Copies jars listed in `tools/<tool>/runtime-bundles.lock` out of a
  shared local cache (`$GRADLE_USER_HOME/caches/pde-pinned-runtime-bundles/`, keyed by filename,
  shared across all four tools and all worktrees on the machine) plus the freshly-built app
  bundle jar and the equinox launcher jar. No JVM subprocess, no network, no p2 metadata parsing.
- **`resolveRuntimeViaP2Director`** + **`regeneratePinnedRuntimeBundles`** -- the OLD, real
  p2.director-based resolution, kept exactly as it was. **Not** wired into `assemble`/`build`/
  `installDist`; run manually or in CI only.

### Why we didn't just check the jars into git

The resolved sets total 80-100+ unique Eclipse SDK jars (tens of MB). Vendoring that much binary
content into the repo would bloat clones/diffs for no real benefit, so only the **lockfile**
(`tools/<tool>/runtime-bundles.lock`, one filename per line) is checked in -- it documents
exactly what's pinned and is a trivial, reviewable diff. The actual jar bytes live in the
Gradle-user-home cache, which is reproducible from the lockfile at any time by rerunning
`regeneratePinnedRuntimeBundles` (it re-resolves via p2.director and repopulates the cache).

## When you need to regenerate

Run, for each tool that needs it:

```
./gradlew :api-analyzer:regeneratePinnedRuntimeBundles
./gradlew :target-installer:regeneratePinnedRuntimeBundles
./gradlew :workspace-setup:regeneratePinnedRuntimeBundles
./gradlew :jdt-build:regeneratePinnedRuntimeBundles
```

This needs the local Eclipse SDK (`eclipseSdk` in `gradle.properties`) and, currently, the
`p2Repositories` remote fallback (still load-bearing for the `osgi.ee JavaSE-21` capability gap
documented in `gradle.properties`). Commit the resulting changes to `tools/<tool>/runtime-bundles.lock`.

Regenerate when:
- The local Eclipse SDK install (`eclipseSdk` path) is upgraded to a new version.
- A tool's `installIUs` list changes (a new bundle dependency is added/removed).
- `materializeRuntime` fails with "Pinned runtime bundle '...' is missing from the shared cache"
  -- this means the lockfile references a filename that isn't in your machine's cache yet (e.g.
  fresh machine, or the cache was cleared). The error message names the exact regenerate command.

Expected to be rare (tied to SDK upgrades), which is the whole point -- if this is happening on
every build, something has gone wrong with the pinning (e.g. the lockfile is being regenerated by
a script/hook it shouldn't be) and is worth investigating rather than working around.

## If you hit a runtime failure that "smells like" a missing bundle

`p2.director`'s dependency resolution is more semantically complete than our lockfile snapshot --
it can also resolve service/capability-based wiring (SCR, extension registry). Because we're
pinning its *past* correct output rather than recomputing the closure ourselves, this only bites
if the runtime's actual behavior at execution time depends on something not present in the
originally-resolved set (for example, a code path that was never exercised when
`regeneratePinnedRuntimeBundles` last ran, but now is). If an Equinox app throws
`NoClassDefFoundError`/`ClassNotFoundException` or fails to find an extension point after this
change, regenerating the pinned set (even without an SDK version bump) is the first thing to try.
